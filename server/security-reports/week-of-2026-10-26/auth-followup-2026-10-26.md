# Authentication follow-up — 26 October 2026

This follow-up implements the first three auth-related checklist items from
`security-hardening-2026-10-26.md`. That report's statement that auth.js was
unchanged describes the earlier review, not this follow-up.

No .env file was inspected or edited. No dependency was installed. No changes
were committed or pushed. Existing unrelated working-tree changes were preserved.

## REV-SEC-24: shared per-account login budget

The login route now validates the request, normalizes its email, and reserves a
counter increment before doing password/MFA work. By default it permits 20 total
login attempts per normalized email per fixed 15-minute bucket, in addition to
the existing IP limits. Correct and incorrect attempts both count. The same
response and counter policy apply to unknown addresses.

`security/accountLoginLimit.js` contains the small shared-counter implementation.
MongoDB atomically increments a document in `loginAccountLimits`; all workers use
the same stable `SESSION_SECRET` to derive a keyed, non-plaintext email digest.
Changing IPs, creating a new session, or restarting with that same secret does
not give a new account budget. Changing the signing secret intentionally changes
the counter namespace as well as invalidating sessions.

The bucket is part of the counter ID. A TTL index cleans old records, but cleanup
timing is not what enforces the window. This is a fixed-window policy, not an
exact rolling-window guarantee. A blocked request gets 429 and `Retry-After`.
Unavailable counter storage returns 503 rather than silently allowing login.
`server.js` waits for the TTL index before opening the HTTP server.

There is no manual database reset or migration: startup creates this supporting
collection/index using the existing database-scoped readWrite account.

**Tradeoff:** an attacker can temporarily exhaust an account's login allowance.
It expires automatically; it does not ban the account or invalidate existing
sessions. This is one defense layer, not complete distributed-bot protection.

## REV-SEC-25: administrator assurance belongs to the login session

`authService.authenticate()` returns `{ user, mfaVerified, mfaEnabledAt }` only
after checking the password and, where enrolled, a real TOTP code. These flags
are generated by the service, not accepted from JSON or copied from a stored
`mfaVerified` field. An administrator without enrolled MFA cannot log in.

The existing `authService.login()` remains available as a wrapper returning only
the user, preserving other callers. The HTTP login route uses `authenticate()`
and writes the assurance into the regenerated server-side session.

`requireAdmin()` now requires all of:

- a valid active account and matching session version;
- the current database role is admin;
- the session was created while signing in as admin;
- this session completed MFA;
- the recorded MFA enrollment timestamp still matches the account.

Changing a member's role alone cannot upgrade its existing session. Missing MFA
assurance in an older admin session fails closed: sign in again. Disabling or
re-enrolling MFA invalidates the recorded enrollment proof; the existing admin
script also changes sessionVersion. Profile routes must still allowlist writable
fields and never permit role/MFA/session-version edits from the browser.

The browser receives the same public user fields as before. Neither the password
hash nor the TOTP secret is put in its JSON response or session cookie.

## REV-SEC-26: CSRF protection before future API routers

After session middleware, `app.js` mounts `auth.csrfForMutations` at `/api`, before
the auth router, protected prefixes, and `mountRoutes`. Every unsafe API method
therefore needs the session's `X-CSRF-Token`, even if an individual router forgets
to attach middleware. Supplied foreign Origin headers are also rejected.

GET, HEAD, and OPTIONS are exempt and must remain read-only. Existing explicit
auth-route CSRF checks remain harmless additional checks. CSRF is not login,
authorization, or proof of a human: post ownership and permissions still belong
in their corresponding routes/controllers.

The frontend pattern remains: bootstrap `/api/auth/csrf` with cookies, then send
the returned token and cookies with mutations. Login rotates the token; use the
new token in its response. Verified webhooks or other non-cookie integrations
would require a deliberate, narrowly scoped design, not a blanket CSRF bypass.

removed by their tests. Test counter collections were injected explicitly so no
normal `loginAccountLimits` collection was touched by integration testing.

From the server directory:

REV_SECURITY_ATLAS=0 npm test

# Real database: new protections plus existing login/reset flows.
REV_SECURITY_ATLAS=1 node --test test/auth-boundaries.test.js test/auth-atlas.test.js

# Additional database scenarios, excluding previously unstable load/timing tests.
REV_SECURITY_ATLAS=1 node --test --test-skip-pattern='login timing|BOT FLOOD:' test/security-database.test.js

`auth-boundaries.test.js` covers atomic races, worker reuse, next-window behavior,
storage outages, normalized emails, changing IPs, role changes, actual MFA and
enrollment checks, missing old-session assurance, unsafe methods, token mismatch,
Origin rejection, and token rotation. The two older LIMITATION tests for stored
role changes and many-IP guessing now assert the repaired behavior instead.

## Still outside this change

- Email ownership verification and a real email delivery adapter.
- The separately reported reset-email accounting/atomicity gaps in requestReset.
- Shared/distributed storage for the other IP-based rate limiters.
- The existing timing/load-test reliability problems and actual hosting capacity.
- Frontend completion and route-level ownership/authorization rules.

These changes address the requested boundaries; they do not certify the whole
application secure or production-ready.
